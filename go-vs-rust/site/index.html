The same in-memory cache, written once in each language, takes the same load on the same machine all day and all night. The graphs below are live. Every merged pull request is marked on them, so you can see what a change did.

  • 2 dedicated cores each
  • 1 GiB memory limit each
  • 5,000 GET/s each, from k6
  • 500,000 entries, LRU eviction

The live numbers

Latency is what k6 measures from outside. CPU and memory come from cAdvisor, per container.

What is running now

Each deploy is a commit on main. The yellow markers on the graphs above are these deploys.

The contenders

Both start from the same design: 64 shards, each one a hash map with an LRU list behind a mutex.

Go

Standard library only: net/http, container/list, sync.Mutex. GOMEMLIMIT is set so the garbage collector knows the container limit.

Rust

axum on tokio, with the lru crate and std::sync::Mutex. Release build with LTO.

The service

Every implementation follows the same spec, and a conformance test checks it before a merge.

RequestAnswer
PUT /kv/{key}204, or 413 above 1024 bytes
GET /kv/{key}200 with the value, or 404
GET /health200 ok
GET /metricsentries, hits, misses, evictions

Make yours faster

Think your language can do better, or want to add a new one? Open a pull request.

  1. Change the code in impls/<language>/Any library, any data structure, as long as it follows SPEC.md and stays inside the limits.
  2. Open a pull requestCI builds the image and runs the conformance test. Nothing from a pull request runs on the benchmark machine.
  3. After review and mergeThe machine picks up main within a minute, rebuilds only what changed and marks the deploy on every graph.
